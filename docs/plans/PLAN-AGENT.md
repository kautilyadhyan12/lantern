# PLAN AGENT — From fixed research rounds to an investigator agent

## Goal

Lantern's research is currently a fixed sequence. It plans, searches the web and news,
triages, reads, extracts, follows up, assesses and writes. The model makes judgements inside
each stage, but it cannot choose *how* to investigate, and its only instruments are web
search, page reading and social search.

This plan turns the research into the investigation loop of `03_AGENT_DESIGN.md` §2:

- A **researcher agent** looks at the case file for one key question at a time.
- It chooses up to four tool calls from a **toolbox**. Each call gets a one-line reason, which
  is shown live.
- A **tool gateway** vets every call before it runs.
- The results become evidence, and the agent decides the next move.
- This repeats until the stop conditions of §2.1 are met.

New tools then give the agent real investigative pivots: official sanctions lists, Wikipedia
and Wikidata, GDELT, and later company registries and domain records. Finally, an
evidence-based **links map** of people, organisations and incidents.

The office rules stay exactly as they are:

- The model proposes; code decides.
- Every quote is checked against the saved source.
- Confidence is computed by code.
- Search results stay transient.
- Captured content cannot trigger any action outside the toolbox.

### AG1a — tool layer (`src/lantern/tools/`)

```python
# tools/base.py
ToolKind = Literal["search", "read", "record"]

class ToolCall(BaseModel):          # what the researcher proposes
    tool: str
    args: dict[str, object]
    question_ref: str
    why: str = Field(max_length=200)

@dataclass(frozen=True)
class SourceDraft:                  # turned into a Source with a ref by the loop
    url: str; title: str | None; published: str | None; body: bytes; text: str
    kind: Literal["page", "post", "record"]; origin: str
    archive_url: str | None = None; archived_at: datetime | None = None
    record_claims: tuple[str, ...] = ()   # statements generated by code (records only)

@dataclass
class ToolResult:
    hits: list[Hit]                 # transient: this step only, never stored
    sources: list[SourceDraft]
    summary: str                    # one line for the case file ("8 results", "no entry found")

class Tool(Protocol):
    name: ClassVar[str]             # "web_search", "news_search", "read_page", ...
    description: ClassVar[str]      # shown to the model in the tool menu
    args_model: ClassVar[type[BaseModel]]
    kind: ClassVar[ToolKind]
    rate_key: ClassVar[str]         # pacing key, e.g. "tavily", "gdelt", "per-host"
    min_interval: ClassVar[float]   # seconds between calls for this rate key (GDELT: 5)
    async def run(self, args: BaseModel, ctx: ToolContext) -> ToolResult: ...

# tools/registry.py
class Registry:
    def register(self, tool: Tool) -> None            # rejects duplicate names
    def get(self, name: str) -> Tool | None
    def menu(self, allowed: Iterable[str], budget: RunBudget) -> str
        # name, description, compact JSON schema of the args, calls left

# tools/gateway.py
@dataclass
class RunBudget: tool_calls: int; searches: int; pages: int; records: int   # remaining

@dataclass(frozen=True)
class Outcome:
    call: ToolCall
    status: Literal["ok", "refused", "duplicate", "failed"]
    reason: str                     # plain words, shown to the next researcher step
    result: ToolResult | None

class ToolGateway:
    def __init__(self, registry: Registry, budget: RunBudget, known_urls: set[str],
                 on_step: Callable[[str], None]) -> None
    async def run(self, call: ToolCall, ctx: ToolContext) -> Outcome
```

The gateway checks each call in this order. Each check is tested once, with fake tools:

1. Unknown tool, or a tool not allowed for this depth: refused.
2. Arguments validated against `args_model`: refused with the validation error.
3. Duplicate (same tool + canonical args): the earlier outcome's summary is returned and nothing is run.
4. URL provenance for `read` tools (`02` §9.4). The URL must be known: given by the user, returned by a search, or linked from a captured source.
5. Budget for the tool's kind: refused when exhausted.
6. Pacing per `rate_key`.
7. Run; failures become `failed` with the adapter's plain message.
8. One step line in the investigation log.

Adapters in AG1a only wrap existing modules:

| Tool | Kind | Args |
|---|---|---|
| `web_search` | search | `query` |
| `news_search` | search | `query`, `time_range?` |
| `read_page` | read | `url` (archive fallback rules unchanged) |
| `social_search` | search | `phrase` or `hashtag` |
| `post_links` | search | `phrase` (leads only, never read) |

### AG1b — the researcher loop (`src/lantern/agent/`, `src/lantern/core/`)

```python
# agent/views.py — case-file views, each with a character cap (03 §4.2)
def brief_view(inv) -> str
def question_view(inv, ref) -> str           # text, kind, status, attempts, current finding
def evidence_digest(inv, ref) -> str         # searches made + counts, top sources, items with
                                             # status, unconfirmed mentions, gaps, refusals
def hits_view(hits) -> str                   # transient, for triage only

# agent/researcher.py
class ResearchStep(BaseModel):
    note: str = Field(max_length=200)        # shown live: what the agent is doing and why
    calls: list[ToolCall] = Field(max_length=4)
    done: bool = False
    done_reason: str = ""

class TriageStep(BaseModel):                 # replaces today's separate triage + discover
    read: list[str]                          # H refs, at most 8
    spotted: list[Spotted]                   # names seen in titles/snippets (as today)

async def next_actions(model, views, menu) -> ResearchStep
    # tool args validated against the registry; one retry with the errors, then skip

# core/loop_rules.py — pure, property-tested
def select_questions(questions, attempts, k=2) -> list[str]   # priority, fewest attempts (03 §2.2)
def should_stop(state: LoopState) -> StopReason | None        # 03 §2.1, first match wins

# agent/loop.py
async def investigate(inv, tools, budgets) -> Investigation   # 03 §2, with existing stages
```

How the loop runs:

- For each selected key question:
  1. The researcher proposes calls.
  2. The gateway vets and runs them.
  3. Search hits go to one triage call in the same step, and the picks are read.
  4. New sources are extracted by the reader model, and the item list is updated.
  5. The assessor re-assesses the question only when its evidence changed.
- A question becomes `unanswerable` after 3 attempts with at least 2 different tools or strategies (`03` §2.1).
- List questions stay open until the researcher declares them done, or there is no progress for 2 rounds.

Budgets replace the fixed depths:

| | Quick look | Deep investigation | Continue |
|---|---|---|---|
| Rounds | 1 | 6 | +2 |
| Pages | 10 | 30 | +16 |
| Tool calls | 15 | 60 | +25 |
| Wall clock | 5 min | 15 min | 8 min |
| Model tokens (all providers) | 60k | 200k | +100k |

The model gateway enforces the token budget. At 85% of any budget (tokens, tool calls, pages, wall clock), research stops and the run moves to assessment and the report. This share is reserved, so a report is always produced, and the report says what stopped it (`02` §13).

Models are routed by role, spreading work over separate free allowances:

- **Researcher, assessor and writer:** `groq:openai/gpt-oss-120b`.
- **Triage and inventory:** a second free model with its own daily quota (`groq:openai/gpt-oss-20b` per `04` §1; re-verify at build time).
- **Bulk reading:** Gemini.
- **Fallback:** each role falls back to the other entries when a quota runs out.

The live log shows one line per researcher step, for example: *"Q1 · step 3 · news_search 'Abu Hashim Lahore fall': a report calls Muhammad Sarwar 'Abu Hashim'; searching the alias for more reporting."*

The report's method section lists the tools used, with counts, and the steps taken.

The fixed rounds stay behind `LANTERN_AGENT=0` until the comparison (AG1b-AC8) shows the agent is at least as good. Then they are removed.

### AG2 — records toolbox (`tools/adapters/`)

**`sanctions_search(name)`** searches the official lists, cached once a day and saved with their sha256:

- The OFAC SDN list: `SDN.CSV`, plus `ALT.CSV` for aliases.
- The UN Security Council consolidated list: `consolidated.xml`.

Matches are on the normalised name and the aliases. Each matching entry becomes a `record` source graded **A**, with record claims generated by code: designation, programmes, aliases, listing reason and "Linked To". The model never writes these. The OFAC file is about 5.8 MB, so this adapter gets a 20 MB size cap.

**`wiki_lookup(query)`** reads the Wikipedia REST summary and the Wikidata entity: labels, aliases in many languages, and a fixed set of properties such as instance of, member of, position held, founded by, date of death and place of death. It is graded **C** (background, `04` §3). It uses Wikimedia's required User-Agent with contact details.

**`gdelt_search(query, timespan)`** uses the GDELT DOC 2.0 article list, paced at one request per 5 s. Its hits go to triage like web search. It is optional: it is disabled automatically when GDELT answers with its rate-limit notice.

The researcher prompt gains short guidance on when each tool helps. For example: "a report says someone is designated, so check the sanctions lists"; "a name has spellings or aliases, so check Wikidata".

### AG3 — entities and links

- `Entity(ref "E1", kind: organisation | person_public_role | place | event, name, aliases, ids)`.
- `Link(subject E, relation, object E, claim_refs, basis: "stated" | "record" | "assessed", status)`.
- The relation vocabulary is fixed and enforced by code: `member_of`, `leader_of`, `founded`, `designated_by`, `linked_to`, `alias_of`, `killed_in`, `located_in`, `reported_by`. There are no relations for protected traits.
- Extraction emits entity mentions and relation triples tied to each claim's anchored quote. Records tools emit links by code, from OFAC "Linked To" and Wikidata "member of".
- Status follows the existing rules: two or more independent origins means corroborated; a record link is rated as the record.
- **Entity resolution:**
  - Organisations and places merge on identifiers and shared aliases.
  - People merge only on an anchor: a record alias, a Wikidata ID, or an explicit "also known as" claim. Never on a similar name (`03` §8.8 and `07` invariant 4).
- An "assessed" link (for example, "these deaths may be connected") is shown as an assessment with its evidence for and against, never as a fact.
- **Links map:**
  - It is an SVG drawn by Lantern's own code (no new dependency under the current Content-Security-Policy).
  - Each line opens the evidence for that link.
  - Clusters can be filtered by type and status.

## Acceptance criteria

### AG1a
- AG1a-AC1 The registry builds each tool's menu entry from its args model and rejects duplicate names.
- AG1a-AC2 The gateway refuses unknown tools, invalid args, unknown URLs for read tools and exhausted budgets before any network I/O, with a plain reason. It returns the earlier outcome for duplicates and paces calls per rate key (fake clock).
- AG1a-AC3 The existing tests pass unchanged; the rounds reach every capability only through the gateway.

### AG1b
- AG1b-AC1 A researcher step returns at most 4 calls, each validated against the registry, or `done` with a reason. Invalid args get one retry with the errors, then the step is skipped and logged.
- AG1b-AC2 `select_questions` and `should_stop` implement `03` §2.1–2.2 and are property-tested (all terminal, round limit, no progress for 2 rounds, budget soft stop at 85 %, wall clock).
- AG1b-AC3 Hits are triaged within the same step (at most 8 reads), spotted names become mentions, and a storage scan finds no hit titles or snippets.
- AG1b-AC4 Refusals and failures appear in the next step's evidence digest, so the agent can change approach.
- AG1b-AC5 The live log shows each step's note and calls. The report's method section lists the tools used and the steps taken.
- AG1b-AC6 Injection canary: a captured page that says to read `https://evil.example/…` or to call an unlisted tool causes no such call. The provenance refusal is logged.
- AG1b-AC7 Quick look, deep investigation and continue run as budgets of the same loop. Everything shipped in #1–#3 still holds: quote anchoring, citation check, ratings, archive rules, leads, social posts, items, mentions, period grouping.
- AG1b-AC9 The token budget per depth is enforced. At 85% the loop stops research and moves to assessment and the report, and the report states that the budget stopped research (fake usage counts).
- AG1b-AC8 Comparison: the same three questions are run with the fixed rounds and with the agent, and the PLAN log records items, corroborated items, pages, tokens and minutes. The fixed rounds are removed only if the agent is at least as good.

### AG2
- AG2-AC1 `sanctions_search` finds an entry by name or alias in both lists. It returns record sources graded A, with code-generated claims for designation, aliases and links, and caches each list for a day with its sha256.
- AG2-AC2 `wiki_lookup` returns the summary and the selected Wikidata properties as a C-graded source with record claims. It uses the required User-Agent.
- AG2-AC3 `gdelt_search` paces itself at one request per 5 s, and turns itself off for the run on the rate-limit notice.
- AG2-AC4 Contract tests replay recorded responses for each source, including "no match" and errors.

### AG3
- AG3-AC1 Entities and links are created only from anchored claims or records. The relation vocabulary is enforced, and there are no protected-trait relations.
- AG3-AC2 People are never merged on name similarity alone (table of near-miss names).
- AG3-AC3 Link status follows the independence rules. Assessed links are labelled as assessments, with their evidence for and against.
- AG3-AC4 The links map renders from the stored entities and links. Every line opens its evidence, and all text is escaped.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| **Token use.** A deep agent run may use 1.5–2× today's tokens (about 150–200k), close to Groq's free 200k/day. | A token budget per depth (60k / 200k / +100k), with a soft stop at 85%. Routing by role spreads the work over models with separate free quotas. Capped views; assess only when the evidence changed; stop on no progress. The live comparison (6 runs) is spread over 2–3 days. A paid model (DeepSeek, about $0.15–0.30 per investigation per `03` §5) is the owner's decision. |
| **Clumsy tool choices** by free models. | Clear tool descriptions with "when to use"; refusals fed back; one-line reasons visible for review; the comparison before the switch-over. |
| **Wandering or loops.** | Duplicate suppression, attempt caps, round and wall-clock limits, the no-progress stop. |
| **Prompt injection.** | Read-only tools; menu-only calls; URL provenance; refs-only outputs; schema validation; the canary test. |
| **People and privacy.** | The safety gate first; no private-person pivots; person entities merge only on anchors; no protected-trait relations; sanctions and Wikidata lookups only for names that appear in evidence. |
| **External availability.** | GDELT throttles this network (seen today); archive.org is slow at times; OFAC's file is larger than the default cap. Each tool fails into a plain refusal the agent can work around. |
| **Run-to-run variance.** | "Continue investigating"; the comparison records variance across repeated runs. |
