# PLAN S0.1 — Repository skeleton, dev container and tooling

## Goal

Prepare a repeatable workspace for Lantern: a small Python project, a local database, a command that upgrades that database, and checks that catch mistakes before work is saved. This story supplies the foundation for later research features. It does not conduct investigations.

## Scope

In: Python 3.12 project and lockfile; the exact tooling configuration from docs/05 §2.1; local Postgres 16 with pgvector; typed secret settings; an empty Alembic baseline; local pre-commit hooks; the custom Python linter; acceptance tests; a beginner-readable README; ignored local data and placeholder settings.

Out: research, model calls, HTTP adapters, application tables, event logging, vector indexing, UI, deployment, CI, agent safety hooks, import contracts and the proof/review tool implementations. Those remain in their assigned stories. No external API keys, paid services, GitHub account changes, or fixture recordings are required.

The user's previously authorized AGENTS.md supply-chain rule is carried onto this branch so it applies to the bootstrap; main remains unchanged. S0.2 will share this branch under docs/08 §5, with its own plan and approval. This plan authorizes neither S0.2 nor a merge.

Public interfaces to implement after approval (signatures are proposals, not code created in this step):

```python
# lantern/config.py
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="LANTERN_", extra="ignore", hide_input_in_errors=True
    )
    database_url: SecretStr  # required; no production credential default

    @field_validator("database_url")
    @classmethod
    def validate_database_url(cls, value: SecretStr) -> SecretStr: ...

# lantern/cli.py — the project console script targets main
# argparse owns help/usage; only `db upgrade` performs work.
def main(argv: Sequence[str] | None = None) -> int: ...

# lantern/db/migrate.py
class MigrationError(RuntimeError): ...
def upgrade(settings: Settings) -> None: ...

# migrations/env.py — Alembic's standard async bridge, not an app service
# Alembic Config.attributes carries the secret; no URL in alembic.ini.
def do_run_migrations(connection: Connection) -> None: ...
async def run_async_migrations() -> None: ...

# versions/0001_baseline.py
# revision = "0001_baseline"; down_revision = None
def upgrade() -> None: ...
def downgrade() -> None: ...

# scripts/lint_custom.py
@dataclass(frozen=True)
class Violation:
    path: str
    line: int
    rule: str
    message: str

def lint_source(source: str, path: str) -> list[Violation]: ...
def main(argv: Sequence[str] | None = None) -> int: ...
```

Settings accept only a well-formed `postgresql+asyncpg` URL with host and database; reject absent/malformed URLs and other drivers using generic, secret-free validation text. Tests use deliberately fake credentials. Do not render raw Pydantic error payloads, connection exceptions, or SQLAlchemy URLs. The CLI catches expected settings/migration failures and returns nonzero with plain guidance; unavailable database guidance points to `make db`.

The migration wrapper locates files relative to its package, not the working directory. It invokes Alembic's Python API without shell commands. The environment uses SQLAlchemy's async engine, `NullPool`, bounded connection and command timeouts, `asyncio.timeout`, `await connection.run_sync(do_run_migrations)`, and disposal in `finally`. Secrets are unwrapped only at engine creation, with parameter hiding and no echo. Alembic's version table is the only table added. Repeat upgrades are idempotent. Baseline upgrade/downgrade create and delete no application data.

Compose uses the verified `pgvector/pgvector:pg16` tag with the manifest digest recorded below to prevent tag drift. Add `pg_isready` healthcheck and bounded retries; map only `127.0.0.1:${LANTERN_DB_PORT:-5434}:5432`. Use a named local data volume. `make db` starts and waits for database health; `make db-down` stops without deleting the volume. Local-only demonstration credentials must be clearly labeled, contain no personal information, and never be reused for deployment. README shows how to set `LANTERN_DATABASE_URL` in the shell without writing a real `.env`.

`make check` runs sequentially and stops on failure: ruff check, ruff format --check, the custom linter, strict mypy, and offline pytest. Include database e2e tests against local Compose; a stopped database fails with a helpful message and never silently skips. No external HTTP/model access is allowed. Test socket controls permit only localhost/Unix sockets needed by the local DB and async loop. A fresh-clone sync check runs separately as an integration check because package downloads are not part of offline pytest.

Copy every tooling key/value from docs/05 §2.1, including marker definitions, rule selection, ignores, branch coverage source paths and the Pydantic mypy plugin. Under the user-approved ADR 0002 update, set `[tool.uv] exclude-newer = false`, retain secure minimum constraints, pin the checked build backend and commit the resolved version/hash lockfile. Check the full resolved graph against current advisories and PyPI artifact metadata before installation. Use `uv add` for dependencies and `uv add --dev` for tools, including the selected Hatchling version; mirror that exact eligible Hatchling pin in build-system.requires so it is both auditable in the lock graph and used for isolated builds. The installed `uv add --help` has no `--build` option. No package installation in this planning step. Before each later addition, explain its purpose, repeat advisory checks, and check resolved transitive packages too. Do not install litellm, Git-based packages, yanked releases, versions with applicable known vulnerabilities, or unverified alternate-index packages. S0.2 adds the permanent dependency-audit gate.

Local pre-commit hooks all use `repo: local`, `language: system`, and commands beginning `uv run`. They cover EOF, trailing whitespace, ruff, ruff format, mypy and detect-secrets. Run mypy over its configured project targets rather than treating arbitrary staged paths as modules. Generate the secret baseline using the scanner, inspect findings without exposing secret values, and never hand-mark real secrets as acceptable.

The custom linter uses AST checks plus tokenized comments, with stable rule IDs for all six forbidden-pattern categories in docs/05 §2.1. Broad handlers are permitted only when they re-raise or call `.exception(...)`; a nested unrelated function does not count. Check suppression reasons and issue URLs, including decorator and function-call forms of skip/xfail. Detect `shell=` expressions except literal `False`. Restrict `print` and `time.sleep` rules to source paths under `src/`; cover normal imported aliases where the AST provides them. This is a static development check, not a Python security sandbox. Report filename, line, rule and remedy; valid Python must never crash the linter.

Bootstrap test environment: tests-first needs pytest before pyproject and make targets exist. After plan approval, prepare only the minimum dependency/config harness required to run the RED suite and signature stubs allowed by the tests-first skill. Log any already-passing infrastructure/regression guards explicitly; do not weaken AC assertions to fabricate RED. Configuration/file tests should fail by assertions explaining missing artifacts, not import/collection errors. The acceptance-ID checker is built in S0.2; report its absence as the tests-first skill directs, rather than prebuilding it.
